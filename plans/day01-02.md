### Measurement specification

- The first generated token comes from the prefill pass. Therefore
  `prefill_s` includes that token. Compute `decode_tok_per_s` as
  `(tokens_generated - 1) / decode_s` only when at least one token was
  generated after prefill and `decode_s` is finite and strictly positive.
  Otherwise leave throughput blank in the CSV, record the reason, and retain
  the raw token count, durations, and end-to-end latency. Report valid and
  undefined repeat counts and use valid throughput values for summaries.
  Leave a speed ratio undefined when either contributing throughput is
  undefined. Carry this convention into the speculative engine.
- Timers start after tokenization, with input IDs already on the device, and
  end after the final `torch.cuda.synchronize()`. `tokens_generated` includes
  EOS when EOS is emitted, and this rule is identical for every method; stop
  at EOS or `max_new_tokens`.
- **End-to-end latency:** `total_s`, measured from the timer start through the
  final synchronization, including prefill, decode, and required loop
  overhead. Record `prefill_s` and `decode_s` separately.
- The baseline CSV must include at least
  `method`, `prompt_id`, `repeat`, `tokens_generated`, `prefill_s`,
  `decode_s`, `total_s`, `decode_tok_per_s`, `dtype`, `seed`, `git_commit`,
  and `model_revision`; `model_revision` is the pinned TinyLlama revision
  recorded in row 8 of `docs/project_spec.md`. It must also include the
  configured batch size, max new tokens, EOS/stopped status, and the run
  configuration identifier used to join the iteration CSV.
- Run the approved untimed warmups for each measured configuration before
